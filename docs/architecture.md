# IGCSE Tutor architecture and delivery

## Implemented milestone

Flask server-rendered browser interface → resource, question and assessment modules → SQLite storage. `resources.py` extracts page-based overlapping text chunks. SQLite FTS5 indexes text; search returns document metadata and page citations. `questions.py` owns original sample questions and deterministic marking. Sessions snapshot question IDs, start time and duration; responses and results persist together in a transaction. A submitted session cannot be remarked. Question answers are rendered only after submission. Results show scores, time and per-question feedback.

The recreated repository includes separate English Literature and Language study pages, 21 original English practice questions, seven maths fixtures, subject-filtered search and persistent nine-category poetry notebooks. The working course is Pearson Edexcel Literature 4ET1, with year/route unconfirmed; Language A/B remains unconfirmed. Question schema supports subject, topic, difficulty, type, options, correct answer, numerical tolerance, explanation, marks and provenance. Uploads require a declared permission basis. Metadata accepts all learning-resource categories, including manually supplied authorised past papers and OneNote exports in PDF/text. No official papers are bundled.

Current retrieval is lexical search, not semantic RAG or an AI tutor. The original samples and Foundation/Higher practice labels are not a claim of board alignment. The results overview identifies subjects and pending reviews but remains a local learner dashboard, not a parent account system. Essays receive null marks with an awaiting-review state and are excluded from automatic totals. No human review/mark-entry workflow exists yet. Additive schema upgrades preserve earlier sessions; per-question seeding installs new examples without duplication. Incorrect answers are visible for review; no automated misconception inference is claimed.

## Domain boundaries and extensions

- **Identity and policy:** users, student/parent relationships, school membership, consent, document entitlements and retention policies. Enforce entitlements before ingestion, retrieval and citation delivery, not only in the UI. No multi-user launch until these controls exist.
- **Knowledge repository:** resource → version → document page → chunk, with owner, board, specification version, topic mapping, type, year/session, source URL, checksum, licence/access policy and extraction status. Add asynchronous extraction, malware scanning, OCR, deduplication, deletion and audit logs. Preserve page/section coordinates for citations.
- **Connectors:** OneDrive, Google Drive and OneNote adapters use scoped OAuth and provider APIs, incremental sync, revocation and propagated permissions. Never embed credentials in documents or logs. OneNote hierarchy maps notebooks/sections/pages to source metadata.
- **Grounded tutoring:** retrieve authorised chunks with subject/specification filters and lexical plus embedding search. Pass bounded excerpts to the configured model and return cited document/page/chunk references. Treat document content as untrusted data. Abstain where sources do not support an answer; evaluate citation accuracy and retrieval quality. Honour licences restricting extraction, sharing or model processing.
- **Paper discovery:** configurable board adapters for Cambridge International, Pearson Edexcel and AQA. Register official domains and permitted feeds/APIs or curated catalogue URLs; check current terms, robots policy and access restrictions before crawling. Use caching, rate limits and human review of ambiguous matches. Catalogue subject, board, specification, component, paper type, tier, year, session, variant, source and access/licence state; link question paper, mark scheme and examiner report. Do not circumvent authentication or download restricted resources. No adapters are active yet.
- **Assessment:** immutable versioned questions and rubrics, structured subparts, model answers, provenance and syllabus mappings. Support multiple-choice, short-answer, numerical, structured responses and essays. Pin question versions in sessions and maintain per-question timing and autosaved drafts. Server-owned timing and submission state govern timed assessments.
- **Board configurations:** versioned specification and paper blueprints define duration, sections, optional-question rules, marks, permitted tools and accommodations. Separate topic practice, examination-style practice and full mocks. Clearly distinguish authentic licensed past papers from AI-generated mock questions. Never invent official grade boundaries.
- **Marking:** exact/numerical checks first; board-specific rubrics for longer responses. AI marks must be labelled provisional, record rubric/model versions and rationale, and support teacher review. Keep model answers hidden until submission; audit overrides.
- **Adaptive learning:** topic evidence from marked attempts, weighted by question difficulty, recency and confidence. Track recurring misconception tags, improvement trends and sufficient-evidence thresholds. Recommend revision and practice into an editable study plan; avoid inferring mastery from a single answer.
- **Parent reporting:** authorised linked-parent views of subject performance, mocks, topic mastery, questions attempted, practice time, coverage, readiness and interventions. Show evidence counts and uncertainty; no unsupported readiness percentage. Separate syllabus exposure from demonstrated mastery.

## Delivery phases

1. **Complete:** PDF/text upload, metadata, indexing and cited search; English and mathematics question repository; Literature/Language guided study pages and poetry notebooks; interactive timed topic practice; saved scores and answer feedback.
2. **Next:** identity/parent linkage and resource access control; upload lifecycle and OCR; versioned question authoring/import; more subjects and short/structured responses; autosaved attempts; authorised retrieval and cited tutoring with evaluation.
3. **Then:** reviewed official-board discovery adapters and paper catalogue; board blueprints; examination-style practice and full mocks; rubric marking and provisional AI marks with teacher review.
4. **Later:** calibrated topic mastery, misconceptions, study-plan recommendations, trend analysis and complete parent reporting.

The English features are a new implementation from supplied handoffs, not an import of the unavailable original ZIP. Subject pages are guided study interfaces, not live specialist agents.

## Validation and limitations

Fourteen automated tests pass. Added coverage includes essay exclusion from automatic totals, human-review persistence, late essays, notebook persistence/escaping, subject filters and upgrades from the earlier SQLite schema. Automated integration tests also cover upload/search/citations, upload permission checks, CSRF, correct marking, result persistence, duplicate submission, server-side expiry, numerical tolerance and PDF extraction. Local HTTP startup and content checks passed for six entry points, including both English subjects and poetry. This verifies server responses inside the cloud environment, not browser access from the parent’s computer or a public deployment. No browser automation, production load/security assessment, AI evaluation or board alignment certification has been performed. SQLite and synchronous extraction suit this development milestone; background workers and production authentication are separate work.

## Model-backed tutoring extension

The original no-AI milestone is now extended by tutoring.py (subject conversations, bounded history and permission-scoped FTS retrieval) and model.py (server-only OpenAI Responses transport). Chat source labels map to saved chunk/page metadata; unmatched references are rejected. Existing resource rows migrate to allow_ai=0 and need explicit external-processing permission. This is lexical RAG when sources are cited, and labelled general tutoring otherwise. No live model evaluation is claimed: provider tests simulate responses, and the deployed service still needs a valid API binding and an actual successful reply. See ai-tutor.md.

## Video explanation module

`videos.py` owns validated YouTube IDs, bounded public oEmbed metadata requests, stored review evidence, recommendation eligibility/ranking and opt-in player construction. Question/rubric link tables keep associations explicit. Only reviewed recommendations appear alongside post-submission practice and scheme-specific tutor feedback. No video contents are fed to the LLM; there is no automatic video understanding or web-review scraping. See video-recommendations.md for access and validation status.
